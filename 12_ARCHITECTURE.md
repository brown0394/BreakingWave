# Architecture — What Is Used, and Why

What this document covers: how the code is organised, which patterns it commits to, and the
reason each one was chosen over the obvious alternative. It is the map between the design
docs and the source tree.

- **Design intent** lives in `01_SOUL.md` and `04_PRINCIPLES.md`.
- **Why any individual call was made** lives in `03_DECISIONS.md`; this document cites the
  decision numbers rather than restating their reasoning.
- **Engine traps** live in `11_ENGINE_NOTES.md`.

**Snapshot date: 2026-09-05.** Decisions 042–055 are logged but **not built** — where one
changes the architecture it is marked **PLANNED** and the shipped shape is described first.

---

## 1. The shape in one paragraph

A single UE 5.6 C++ runtime module. Player-facing framework classes (GameMode,
PlayerController, Character, CameraManager) are stock Unreal, subclassed once in C++ and
once more in Blueprint for asset wiring. Everything that is not the player is a
**data-oriented manager**: one actor that owns a flat `TArray` of state structs and ticks
them in a loop, with NPC actors demoted to inert visual shells. All shooters — MG, enemy
rifle, player rifle — push into **one shared bullet array**. All tunable numbers live in
per-system `USTRUCT` settings blocks that the telemetry recorder dumps by reflection at the
start of every session. The level itself is not hand-placed: it is generated by idempotent
editor-Python scripts in `Tools/`.

## 2. Layer map

```
  Config/ + Content/FirstPerson/Blueprints/     BP leaves — asset refs, input assets, no logic
  ────────────────────────────────────────────
  ABreakingWavePlayerController                 death -> takeover phase machine (owns the loop)
  ABreakingWaveCharacter                        input, movement, prone, rifle, hit resolution
  ABreakingWaveCameraManager                    pitch clamps
  UHeadbobShakePattern / UHitCameraShake        all camera motion, via the engine shake system
  ────────────────────────────────────────────
  AMGBunkerManager      -> TArray<FMGBunkerState>          + TArray<FMGBullet>  (shared)
  AAllySimManager       -> TArray<FSimAlly>
  AInfantryManager      -> TArray<FInfantrySoldierState>
  ────────────────────────────────────────────
  AMGBunkerGun, AInfantrySoldier                visual shells: mesh, audio, ragdoll. Tick OFF
  ────────────────────────────────────────────
  FPlaytestRecorder (plain struct, inside the MG manager) -> Saved/Playtests/*.csv
  Tools/*.py, Tools/*.ps1                       level generation, asset generation, analysis
```

## 3. The load-bearing choice: managers over actor-per-NPC

**What.** Every NPC system is `AActor` + `TArray<FSomeState>` + a `for` loop in `Tick`.
`AMGBunkerManager::Tick` (`Source/BreakingWave/MGBunkerSystem.cpp:217`) walks its bunker
array, then advances the bullet array, then samples telemetry.
`AAllySimManager` (`BeachAllySim.h:130`) and `AInfantryManager`
(`BeachInfantrySystem.h:181`) have the same shape. The visible actors —
`AMGBunkerGun` (`MGBunkerSystem.h:363`) and `AInfantrySoldier` (`BeachInfantrySystem.h:169`)
— carry mesh components and nothing else; both set `PrimaryActorTick.bCanEverTick = false`
in their constructors, and both headers say "Visual shell only (Decision 021)" in one line.

**Why.** Decision 021. The design calls for dozens of simultaneous NPCs with density curves,
type ratios and distance tiering. Per-NPC `AAIController` + Behavior Tree + Blackboard fights
that on three fronts: tiering becomes bespoke work instead of "how often do I touch this array
element", behaviour scatters across BT assets that cannot be read in a diff, and the code stops
resembling the documents, which already think in pools and ratios rather than in agents. One
loop over one array is also the only version a two-person team can hold in its head
(Principle 6) and the only version where "what does the gunner do" has a single answer at a
single call site (Principle 7).

**What it bought, concretely.** Decision 029 — the allied wave existed as pure data, targeted
for real by the MGs, months before any ally was rendered. Decision 042 (PLANNED) then removes
the LOD boundary entirely, which is only affordable because behaviour was never coupled to an
actor in the first place.

## 4. The engine boundary: framework classes stay stock

`CLAUDE.md` draws the line explicitly — "fighting the engine is not the goal" — and the tree
holds it. Where the engine already has the machinery, the project rides it:

| Feature | Rides on | Decision |
|---|---|---|
| Prone | `ACharacter` crouch (capsule shrink, clearance check) | 023 |
| Headbob, hit shake, death rattle | `UCameraShakePattern` via `PlayerCameraManager` | 026 |
| Death fade + audio duck | `StartCameraFade(..., bFadeAudio)` | 040 |
| Debug keys | `DebugExecBindings` in `Config/DefaultInput.ini` | 024 |
| Input | Enhanced Input `IA_*` / `IMC_Default` assets | — |

The three player-facing C++ classes are `UCLASS(abstract)`; the instantiable leaves are
`BP_FirstPersonCharacter`, `BP_FirstPersonPlayerController` and `BP_FirstPersonGameMode`,
and `GlobalDefaultGameMode` points at the BP. **Blueprint's job here is asset wiring, not
logic** — meshes, anims, sounds, input assets. No gameplay lives in a graph.

The headbob case is the clearest statement of the rule: a hand-rolled camera offset in
`Tick` would have been simpler on day one, and was rejected because every later shake would
then need to coordinate with a second, parallel camera pathway.

## 5. Behaviour in code, variation in data

`FRifleProfile` (`RifleProfile.h:9`) is the pattern in miniature: **one rifle system, two
data rows.** The player's semi-auto and the defenders' bolt-action are the same fire code
reading different numbers, `bBoltAction` included (Decision 035). Nothing subclasses.

This generalises into the PLANNED work: Decision 043 merges `BeachAllySim` and
`BeachInfantrySystem` into one soldier system where **sides differ in data — lane graph,
target team, anims, voice — never in code**, and Decision 054 makes ally marksmanship its
own spread row rather than its own model. The stated reason is drift: two implementations
that must agree forever diverge the moment either is tuned.

## 6. One settings struct per system, and the numbers are reflected

`CLAUDE.md` requires every tentative number to be a named constant in one obvious place.
The mechanism is a single `EditAnywhere` `USTRUCT` per system, exposed with
`meta = (ShowOnlyInnerProperties)`:

`FMGSettings` (~70 knobs), `FAllySimSettings`, `FInfantrySettings`, `FTransitionSettings`,
`FHeadbobSettings`, `FHitShakeSettings`, `FCorpseSettings`, `FRifleProfile`.

The payoff is not tidiness. Because they are `USTRUCT`s, `FPlaytestRecorder::AppendSettingsDump`
walks them **by reflection** and writes the full settings snapshot into the header of every
session CSV. Tuning changes are therefore attributable per session without anyone remembering
to record them — which is what makes the numbers in `03_DECISIONS.md` measurements rather
than opinions (Decisions 033 and 041 were both driven by that data).

## 7. One bullet pipeline, every shooter

**What.** `FMGBullet` (`MGBunkerSystem.h:288`) is a ~40-byte struct: position, velocity,
remaining life, an `EMGBulletSource` tag (`Gun` / `PlayerRifle` / `InfantryRifle`) and a
source index. `AMGBunkerManager` owns the one array; everyone shoots by calling
`SpawnBullet`. `UpdateBullets` advances each round by `Velocity * DeltaSeconds`, does one
world trace plus segment-vs-capsule tests against sim allies, infantry, MG crew and the
player, and resolves the hit according to the source tag. Flyby crack, whizz banding, sand
impacts and tracers all fall out of the same loop.

**Why projectiles and not hitscan (Decision 030).** Travel time is gameplay, not flavour.
At beach ranges a burst takes 0.5–0.7 s to arrive, so "I moved and it landed where I was" is
physically true, and accuracy numbers tuned against real flight survive into later work —
hitscan-tuned numbers would have had to be re-tuned on the swap. Cost is trivial: well under
100 live rounds with three guns firing.

**Why one array and not one per shooter (Decision 035).** The collision matrix is a property
of the round, so it belongs on the round. Adding the player's rifle meant adding an enum row
and its exceptions (player rounds pass through allies and skip the crack, because your own
rounds do not snap at your ear), not a second ballistics system. Decision 044 adds
`AllyRifle` the same way.

## 8. Cross-system references are integer IDs

Both managers define the same two constants:

```cpp
static constexpr int32 PlayerTargetId = -1;
static constexpr int32 NoTargetId     = -2;
```

Anything ≥ 0 is an index into the ally array. Targets, awareness records, telemetry rows and
bullet ownership all travel as `int32`, never as pointers. Slot reuse is made safe by
`FSimAlly::Generation`, bumped on every reuse so a stale `FMGAwareness` can tell that a fresh
soldier now occupies an old slot — the standard handle/generation pattern, and the reason
recycling a dead ally's slot cannot silently transfer the gunner's attention to a new man.

Actor-to-actor links, where they exist at all, are `TWeakObjectPtr` (`FMGBunkerState::Gun`,
`FInfantrySoldierState::Shell`), so a destroyed shell degrades to "no visual" instead of a
dangling pointer.

## 9. Wiring is discovery at BeginPlay

No manager holds an `EditAnywhere` pointer to another manager. Each one runs `TActorIterator`
in `BeginPlay` to find its peers and its shells (`MGBunkerSystem.cpp:123–137`,
`BeachInfantrySystem.cpp:44–55`). The level therefore carries no reference graph to maintain
— `Tools/PlaceMGCrew.py` drops one manager plus N guns and the manager finds them.

**The cost is on the record.** Decision 043 names it: `Soldier.Shell = *It` means every
enemy soldier must be a hand-placed level actor, which is exactly what blocks scaling to a
40–60 man defence. The PLANNED fix is a runtime pool with shells attached on proximity, which
removes the discovery step for soldiers while keeping it for managers.

## 10. The death → takeover loop is a phase machine on the PlayerController

**What.** `ETransitionPhase` (`BreakingWavePlayerController.h:20`) ticked in `PlayerTick`:
`DeathShake → DeathDescend → DeathHold → FadeOut → [narrative screen] → takeover → FadeIn`.
Durations are `FTransitionSettings` knobs. The death camera is a spawned `ACameraActor`
driven by scripted math, never the ragdoll. Takeover runs at the **end** of the fade, so the
man taken over is alive at the instant he is taken.

**Why here and why this shape.** This loop is priority 2 in `01_SOUL.md` and the thing the
whole game stands on, so it gets an explicit state machine rather than a chain of timers.
Three structural choices carry weight:

- **The narrative screen is a zero-duration state that already exists.** Decision 038 part 1:
  the written half of Step 5 drops into that seam without reshaping anything around it.
- **A new pawn is spawned and possessed per life** (Decision 040 part 2). Per-life state is
  then fresh by construction rather than by remembering to reset it — it removes the whole
  class of "started this life already wounded / already prone / with the last man's magazine"
  bugs that would surface sessions later. It also gives the corpse somewhere to live.
- **The new life inherits the simulation's state, not a zone script** (Decision 040 part 4):
  heading, prone-or-advancing and a partial magazine come from the `FSimAlly` you take over.
  A scripted table would have claimed "in cover behind a berm" for a man who was sprinting in
  the open. The sim is the truth of the world.

Protection after takeover is an **awareness lockout**, not invincibility (Decision 016/040
part 5): MG awareness is zeroed and accrual blocked so the guns genuinely forget the spot,
then must re-acquire through the normal perception ramp; infantry get a flat exclusion.
Rounds already in flight stay live.

## 11. Rendering is the only level of detail — PLANNED (Decision 042)

The unrendered ally simulation was a rendering-cost choice and is explicitly **not** a design
boundary. The planned rule: all soldiers run identical behaviour wherever they are; a shell
attaches when a man enters the render bubble and detaches when he leaves, and nothing about
him changes when it happens.

The reasoning is worth carrying forward because it is the general form of the argument in
§5: behaviour LOD does not solve the smooth-transition problem, it *creates* it — two
behaviour models need a reconciliation boundary, and that boundary is where every pop and
teleport comes from. One model has no transition to get wrong. Affordability was measured,
not assumed (~25–30 skeletal meshes worst case at a 50 m attach radius).

## 12. The level is authored by editor Python

Twenty scripts in `Tools/` place geometry, generate assets, wire input, synthesise
placeholder audio and retarget animations. House rules, visible in every script header:

- **Idempotent and tag-scoped.** Everything spawned carries a tag (`FOG_TAG`, `MG_TAG`);
  re-running deletes the previous batch first. Iterating a layout is edit-constants-and-rerun.
  Two edges this pattern hit in `PlaceFog.py`, both worth copying: a script that **adopts** a
  pre-existing actor rather than spawning one must exclude it from its own sweep, and
  **renaming a tag strands every actor already carrying the old one** — the sweep has to
  keep matching the legacy tag or the previous batch becomes permanent.
- **Coordinate tables live in the script, not in C++.** Decision 052 rejects a compiled node
  table by name: coordinates in two places drift. The trench takes this furthest — one
  hand-authored centreline emits *both* the geometry and the `TrenchNode` actors the soldier
  manager reads at `BeginPlay`, so trench geometry and trench navigation cannot disagree.
- **Two headless tiers**, because the editor is not uniformly scriptable: `-run=pythonscript`
  for asset work, full offscreen editor for anything touching UI, and actor spawning is
  editor-only (it access-violates headless). `11_ENGINE_NOTES.md` holds the full list.
- **C++ as a scripting escape hatch.** `UBlendSpaceTool` (`BlendSpaceTool.h`) is a
  `UBlueprintFunctionLibrary`, `WITH_EDITOR`-guarded, that exists solely to expose blendspace
  triangulation rebuild/inspection to Python — because the engine only rebuilds it inside a
  Persona widget that crashes when opened offscreen.

## 13. Telemetry is a system, not a debug feature

`FPlaytestRecorder` (`PlaytestRecorder.h:64`) is a **plain C++ struct held by value** inside
`AMGBunkerManager` — no `UObject`, no subsystem, no lifetime question. It auto-records every
PIE session to `Saved/Playtests/session_<stamp>.csv`: the reflected settings dump, 2 Hz player
samples, and per-event rows for shots, impacts, cracks, deaths, takeovers, stops and target
switches. `Tools/AnalyzePlaytests.py` aggregates it with plain system Python.

**Why it earns a place in the architecture.** `CLAUDE.md` declares every number tentative,
which is only a workable stance if the game measures itself. The unit of measurement is a
**life**, with a session tally on top, because death chains into a takeover rather than
resetting — the structure follows the loop the game actually has.

The cost is a synchronisation seam that no compiler checks: `Playtest::ZoneBoundariesY` and
`InfantryShooterIdBase` (`PlaytestRecorder.h:17–22`) are duplicated as `ZONE_BOUNDARIES_Y`
and `INFANTRY_SHOOTER_ID_BASE` in `Tools/AnalyzePlaytests.py:31–33`. Both files carry a
comment saying so. If zones move, both move.

## 14. Feedback has no UI layer, so it routes through camera and audio

`01_SOUL.md` forbids health bar, crosshair, ammo counter and minimap. Architecturally that
means there is no HUD class and no widget tree to update — the channels that would normally
be UI are instead:

- **Camera** — `UHeadbobShakePattern` (state: moving / stationary / prone / airborne),
  `UHitCameraShake` (directional push away from the round's travel), the death camera.
- **Audio** — supersonic crack inside 3 m, whizz out to 15 m, sand impacts, the enemy
  bolt-cycle clack that tells you the window is open (Decision 037), distance-delayed MG
  fire loop.

`UMG` and `Slate` remain linked in `BreakingWave.Build.cs` and a mobile-controls widget class
remains on the controller; both are First Person template inheritance, not project design.

## 15. Debug surface

Debug features are `UFUNCTION(Exec)` console commands bound through `DebugExecBindings`
(Decision 024): **F6** `DebugThirdPerson`, **F7** `MGDebug`, plus `MGNoDamage` and
`MGKillCrew` typed at the console. They compile out of Shipping and cannot leak into the
game, and — the reason for the rule — `UEnhancedInputComponent` deletes `BindKey`, so raw
C++ key binds do not compile at all. Game input never mixes with debug input.

## What the architecture deliberately is not

- **No AIControllers, Behavior Trees, Blackboards or perception components.** `AIModule` is
  still in `PublicDependencyModuleNames` and `StateTree` / `GameplayStateTree` are still
  enabled in `BreakingWave.uproject`, but **nothing in `Source/` references any of them**.
  That is template inheritance, not architecture. Do not read the plugin list as intent.
- **No component-based composition of behaviour.** Behaviour is not sliced into
  `UActorComponent`s per NPC; it is a function that takes a state struct.
- **No inheritance hierarchy for NPCs.** There is no `ASoldier` base with ally/enemy
  subclasses, and Decision 043 rules one out permanently in favour of data rows.
- **No gameplay in Blueprint.** BPs hold asset references and nothing else.
- **No save system, no inventory, no progression, no networking.** Single-player, single
  session, and death is continuation rather than retry (Principle 1).

## Where it strains today

Stated plainly so the next session does not rediscover it:

1. **`AMGBunkerManager` is the de facto combat hub and is named after one of its jobs.** At
   1,197 lines it owns the shared bullet array, hit resolution for every entity, the flyby
   and impact audio, and the telemetry recorder. Anything that shoots must reach into the MG
   manager. This is a naming and ownership debt, not a correctness one.
2. **Two soldier implementations exist.** `BeachAllySim` and `BeachInfantrySystem` are
   converging on the same behaviour set from opposite directions. Decision 043 merges them —
   a ~850-line rewrite during which **nothing is playable** — and keeps `BeachAllySim` as a
   deliberately reachable debug path so it cannot rot into dead code.
3. **Constants are duplicated across the C++/Python seam** (zone boundaries, infantry shooter
   id base, barrel length) and held in sync by comment convention only.
4. **Discovery is silent on failure.** A missing manager in the level means `TActorIterator`
   finds nothing and the system does nothing, with no error. Placement scripts are the only
   guarantee the level is correct.
5. **Perception is O(guns × allies) per evaluation tick** and `AdvanceAlly` is one ground
   trace per ally per tick. `02_STATUS.md` already records the intended answer if it bites:
   slice perception across ticks, do not shrink the wave.

The actionable form of this section — 13 items, each tagged with the workstream it
should ride with — is the **Code-health checklist** in `02_STATUS.md` Next Steps.

## Invariants to preserve

Breaking any of these breaks something the docs promise, not just something stylistic.

- NPC behaviour stays in a manager loop over structs; new NPC actors stay tick-disabled shells.
- New shooters add an `EMGBulletSource` row, never a second bullet system.
- New tunables go into an existing settings `USTRUCT`, so they land in the telemetry snapshot.
- Sides and roles differ by data row, never by subclass.
- The transition state machine keeps its zero-duration narrative seam.
- Post-takeover protection stays an awareness lockout; there is no invincibility anywhere.
- Level coordinates stay in `Tools/`; C++ reads what the scripts placed.
